# Инструменты сайта

## check_products.py — контроль актуальности товаров

Проверяет все товары из `products` в front matter статей (`content/*.md`) по карточкам
Яндекс Маркета (регион не задаётся — Москва по умолчанию), сверяет с данными в статьях
и с прошлым снимком, пишет снимок и отчёт.

```
.venv/bin/python tools/check_products.py                    # только проверка, статьи не меняются
.venv/bin/python tools/check_products.py --apply            # + точечно обновить front matter статей
.venv/bin/python tools/check_products.py --only atoll-1713-gs   # одна метка (можно повторять флаг)
.venv/bin/python tools/check_products.py --dry-run --only a,b   # без записи (статьи, снимок, отчёт), решения — в консоль; метки через запятую
.venv/bin/python tools/check_products.py --limit 3          # первые N товаров (отладка)
.venv/bin/python tools/check_products.py --no-links         # не проверять партнёрские ссылки (быстрее)
```

Нужны Python 3.12 и PyYAML (как для `build.py`); остальное — стандартная библиотека.
Запросы идут строго последовательно, пауза 6–10 с (случайная), таймаут 40 с, до 2 повторов.
Полный прогон из ~21 товара занимает около 10 минут (на товар: карточка + проверка ссылки).
Код выхода всегда 0; в конце — короткая сводка и путь к отчёту.

### Что извлекается

Из HTML карточки берутся данные именно этой карточки (по id из `url` в `affiliate.json`):
наличие и цена основного оффера, рейтинг, число оценок — из JSON-LD `Product` с
`"sku":"<id>"`; «купили» — из блока `product-rating-description-item`; название — оттуда же.
Если поле не нашлось — `null`, в отчёте попадает в «Требует решения». Ссылка
`ref_link_no_erid` (и `aff_url`, если задан) проверяется редиректом: id в `/card/.../<id>`
должен совпасть с id карточки.

### Где результаты

- `data/snapshots/YYYY-MM-DD.json` — снимок: все извлечённые поля, время, ошибки, регион;
- `data/reports/YYYY-MM-DD.md` — отчёт: таблица сравнения, «Обновлено автоматически»,
  «Требует решения» (нет в продаже, карточка пропала, ссылка битая, рейтинг < 4.3 или
  упал на ≥ 0.2, данные не извлеклись);
- `data/backups/` — копии статей перед правкой через `--apply`.

### Что делает --apply

Правит только значения в блоке нужной метки в front matter, остальной файл и тексты статей
не трогает (перед записью — бэкап в `data/backups/`):

- `price` — если цена на Маркете отличается от указанной больше чем на 10 %
  (кроме меток с `"price_is_sum": true` в `affiliate.json`: там цена в статье — сумма нескольких
  карточек, она не обновляется, а в отчёте идёт пометка «проверить вручную»);
- `rating`, `reviews`, `bought` — если отличаются;
- товар недоступен — добавляется `status: unavailable`; вернулся в продажу — строка удаляется;
- если в статье что-то изменилось — `updated:` ставится на сегодняшнюю дату.
- `prices_checked: <сегодня>` ставится статье, у которой ВСЕ товары успешно загрузились в этом прогоне (карточка `ok`; не ставится при частичном прогоне `--only`/`--limit` и при любой ошибке загрузки). `updated` из-за него одного не меняется. Из этого поля сборка берёт дату цен в тексте (см. ниже).

Товар со `status: unavailable` на сайте: вместо кнопки — серая плашка «Сейчас нет в
продаже», карточка приглушена, в JSON-LD `ItemList` не попадает, из блока «Наш выбор»
скрывается. После `--apply` нужно запустить `.venv/bin/python build.py`.
Решения из раздела «Требует решения» (замена модели, правка текста) принимаются вручную.

## Награды (rewards.js)

Зачем: Маркет отдаёт реферальную награду (`referralReward`) только залогиненному пользователю, поэтому
`check_products.py` её не запрашивает. Модели с наградой 0 ничего не приносят — их нужно заменять.

Как запустить: открыть market.yandex.ru (с входом), заполнить `URLS` в `tools/rewards.js` ссылками
карточек, вставить код в консоль браузера. В конце выводится JSON `{url: награда_в_рублях}`
(0 — награды нет, null — ошибка запроса).

Куда записать: в запись метки в `affiliate.json` поле `reward_rub_<ГГГГ_ММ_ДД>` (например,
`reward_rub_2026_10_13`). `check_products.py` берёт последнее по дате поле и выводит раздел
«Награда 0 (по affiliate.json)»; метки с нулём попадают и в «Требует решения».

## Проверка текста и сайта (только отчёт, ничего не правят)

Оба скрипта запускаются автоматически в конце `check_products.py` (локальный режим, без сети) и
дописывают свои разделы в `data/reports/<дата>.md`. Ошибка внутри них в отчёт попадает строкой
«ошибка проверки …» и не ломает основную проверку. Вручную: `.venv/bin/python tools/check_text.py`,
`.venv/bin/python tools/check_site.py` (печать в stdout; `--out FILE` дописывает в файл). Код возврата всегда 0.

**`check_text.py`** — цены в тексте против `price` товаров статьи.
- Ищет «N ₽», «N руб.», «~N ₽», «5 тыс. ₽», числа с пробелом/неразрывным пробелом («3 649 ₽») в теле статьи
  и в title/description/seo_*. Цена привязывается к ближайшему слева имени товара в той же строке
  (до 120 символов, без границы предложения и без другой цены между ними). Расхождение > 10 % — в отчёт.
- «от X до Y ₽» — сравнивается с min/max цен товаров статьи, но только в строках со словом «модел…».
- Товары со `status: unavailable` не учитываются в min/max для «от N ₽», «от X до Y ₽» и сравнительных утверждений, но цена рядом с их именем сверяется.
- «до N ₽» — не ошибка; в отчёт идёт, если названный товар дороже порога: в строках таблиц/списков под
  заголовком `##`/`###` с «до N ₽» и в строках, где имя товара стоит сразу после «до N ₽» (≤ 80 символов).
- Даты «цены на 7 октября», «на 07.10» (в строках со словом «цен»/«по состоянию») старше 14 дней.
- Дзен (`../dzen/*.md`): имена товаров из всех статей, цены рядом (расхождение > 10 % с ближайшей ценой
  товара), товары со `status: unavailable` во всех статьях.
- «5,4 тыс. ₽» / «5.4 тыс. ₽» читаются как 5400 (десятичная дробь только перед «тыс»).
- Числа отзывов/оценок/покупок/рейтинга («N оценок», «N отзывов», «N покупок», «купили N», «рейтинг X.X»,
  «X.X из 5», «★ X.X»): в полях карточки subtitle/feature/who/reviews_text/pros/cons и в теле у имени товара
  (та же привязка, что у цен). Находка: рейтинг ±0,05; оценки > 5 % и > 2 шт.; покупки > 10 %; «около N» — 10 %;
  «N отзывов» — только если N больше `reviews` (отдельного поля для текстовых отзывов нет). Пороги «от/до/более N» пропускаются.
- Сравнительные утверждения («самый дешёвый», «самая низкая цена», «самый популярный», «больше всего отзывов…»)
  у имени товара — сверка с min price / max bought (reviews) среди товаров статьи; предупреждение, возможны ложные.
- Цены < 1000 ₽ (аксессуары), диапазоны «500–800 ₽» и `[[minitable]]` не проверяются; сомнительную привязку
  скрипт пропускает: лучше пропустить, чем засорять отчёт.

**Дата цен (`prices_checked`).** Во front matter каждой статьи/калькулятора с `products` — обязательное поле `prices_checked: ГГГГ-ММ-ДД`. В тексте вместо ручных дат — `{{prices_date}}` («19.10.2026») и `{{prices_date_text}}` («19 октября 2026»); `build.py` подставляет их из поля, при его отсутствии сборка падает с указанием статьи. `check_text.py`: `prices_checked` старше 14 дней или не задано — в «Устаревших датах цен» (строка `статья:prices_checked`); оставшиеся ручные даты в тексте ловятся как раньше.

**Раздел «Перечитать после изменения цен»** (пишет `check_products.py` в отчёт после «Требует решения»; в `--dry-run` — в консоль). Для товаров, у которых в этом прогоне цена изменилась > 10 % (то, что применяет `--apply`), рейтинг ≥ 0,2 или число оценок > 20 % и ≥ 5 шт, — таблица «Статья:строка | Строка (≤ 140 симв.)» по всем статьям, где товар упомянут: id в шорткоде `[[product:..]]`/`[[minitable:..]]`, имя товара (та же привязка, что у цен) и строки его карточки про цену/оценки. Старая цена берётся из front matter до правки (git не нужен: сравнение делается внутри прогона, до записи). `check_text.reread_section(changes)` можно вызвать и вручную.

**Раздел «Товар в нескольких статьях: данные расходятся»** (`check_text.py`, входит в число находок): один id в нескольких статьях — сравниваются `price` (> 3 %), `rating` (≠), `reviews` (> 2), `bought` (> 2 и > 5 %), `warranty`/`material` (строки различаются, если заданы в обеих). Отдельный раздел-предупреждение: списки `pros`/`cons` почти совпадают (≥ 2 общих пункта, различаются ≤ 2 пунктами).

**`check_site.py`** — собранный `docs/`.
- Внутренние ссылки/картинки (href/src, включая абсолютные на santehrazbor.ru) → файл существует; якоря `#id` →
  id есть на целевой странице; остатки `[[`, `]]`, `AFF:` в видимом тексте; все svg парсятся как XML.
- sitemap.xml: все URL есть в `docs/`, все страницы (кроме 404 и noindex) есть в sitemap.
- Партнёрские ссылки на market.yandex.ru/ya.cc: в URL есть `erid`, на странице есть текст «Реклама»
  (так реализовано в build.py: erid в query + метка «Реклама ⓘ»).
- `--live`: GET `https://santehrazbor.ru/<путь>` для страниц из sitemap, ждёт 200 (нужна сеть; в
  `check_products.py` не включается).

## indexnow.py — уведомление поисковиков о новых и изменённых страницах

Запуск из `site/` после деплоя: `.venv/bin/python tools/indexnow.py`.
- Читает `docs/sitemap.xml` (loc + lastmod), ключ — `indexnow_key` из `config.json`; файл ключа
  `static/<key>.txt` попадает в корень сайта при сборке и должен быть доступен по https до первой отправки.
- По умолчанию шлёт только URL, у которых lastmod новый или изменился относительно
  `data/indexnow_last.json`; `--all` — все URL; `--dry-run` — только список, без сети и записи состояния.
- POST на `yandex.com/indexnow` и `api.indexnow.org`, печатает код ответа каждого. Состояние обновляется,
  если хотя бы один ответ 200/202. Ошибка сети — сообщение и код выхода 1.

## market_questions.py — вопросы покупателей

Еженедельно собирает НОВЫЕ вопросы покупателей и НОВЫЕ ответы продавцов с карточек Маркета для всех товаров статей — материал для FAQ и списков минусов.
- Запуск из `site/`: `.venv/bin/python tools/market_questions.py`; `--init` — заполнить состояние текущими вопросами без отчёта (первый запуск, после добавления много новых товаров); `--dry-run` — отчёт в stdout, ничего не пишет.
- Товары — из шорткодов `[[product:id]]` в `content/*.md` (все статьи), id карточки — из `affiliate.json`. Товар из нескольких статей запрашивается один раз, в отчёте он стоит под каждой статьёй. Страница `market.yandex.ru/card/x/<id>/questions` через `curl`, пауза 1,5 с. Новый товар без состояния только запоминается.
- Файлы: состояние `data/market_questions_seen.json` (`{товар: {id вопроса: число ответов}}`, старые вопросы не удаляются); отчёт `data/reports/questions-<дата>.md` (по статьям и товарам: `[новый вопрос | новый ответ] (ГГГГ-ММ) вопрос → ответ продавца`, до 400 знаков).
- Капча или блокировка: инструмент останавливается, не обходит её, записывает в отчёт товар, на котором прервался, сохраняет состояние по уже проверенным товарам и завершается с кодом 2. Сетевые ошибки по отдельному товару пропускаются и перечисляются в отчёте.
- Выдача Маркета немного плавает (часть вопросов то появляется, то нет), поэтому старые вопросы остаются в состоянии, а после `--init` лучше прогнать его 2–3 раза подряд — состояние объединяется.
- Что делать с отчётом: рутина предлагает правки FAQ и минусов в плане (`notes/plan-<дата>-weekly-fixes.md`); тексты правит основная сессия. Источник фактов — ответ продавца, в тексте помечать «(ответ продавца)»; вопрос покупателя сам по себе фактом не является.

## Защита от мусорных цен
Автоприменение цены/рейтинга/оценок отключается и запись уходит в «Требует решения», если: на карточке
«Разобрали в магазине» (`main_sold_out`: цена и оценки тогда от других магазинов), в заголовке «N шт в упаковке»
(`multipack`), цена отличается от прошлого снимка больше чем на `PRICE_JUMP_MAX` (40 %). Пропавший рейтинг из статьи не удаляется.
